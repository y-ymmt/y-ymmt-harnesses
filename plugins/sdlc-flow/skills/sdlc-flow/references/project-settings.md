# プロジェクト設定の読み方

sdlc-flow は、プロジェクトごとに違う決まりをそのプロジェクトの文書から読み取って使う。専用の設定ファイルは作らない。
文書の置き方はプロジェクトによって違う。そこで、多くのプロジェクトで概要が書かれている**入口の文書**から読み始め、
そこから案内されている文書をたどる。

## 探し方

1. **ユーザーが直接言ったこと**（このコマンドの引数やチャット）を最優先にする
2. **入口の文書**を読む: リポジトリ直下の `README.md`、`CLAUDE.md`、`AGENTS.md`（あるものすべて）。サブディレクトリの CLAUDE.md も含む
3. **入口から案内されている文書をたどる**: 開発手順・規約・設計・運用の文書へのリンクや記述（例: `docs/development.md`、`docs/` 配下、Wiki の URL、
   `CONTRIBUTING.md`）。集める項目に関係する文書だけを読み、無関係な文書までは広げない
4. **決まった場所の文書**を確かめる: `.claude/rules/`、`REVIEW.md`、`CONTRIBUTING.md`、`.github/pull_request_template.md`
5. **ビルド定義**から分かることを補う: `Makefile`、`package.json` の scripts、`pyproject.toml`、`justfile`、CI の定義（`.github/workflows/` など）

食い違いがあれば、上の番号の小さいものを優先する。2〜4 の中では、より具体的に書かれているほうを優先する。

## 集める項目

| 項目 | 例 | 見つからないとき |
|---|---|---|
| 仕様の調べ方 | 「仕様は Notion が正。調査は専用のサブエージェントに任せる」 | 仕様書の場所を聞く。無ければチケットとコードだけで進める |
| チェックコマンド | `make test`、`make lint`、`npm run typecheck` | ビルド定義と CI から候補を出して確かめてもらう |
| ブランチの命名規則 | `feature/PROJ-12-description` | `feature/<チケット番号>-<説明>` を使う（聞かない） |
| コミットメッセージの書式 | 「チケット番号＋日本語の要約」 | 直近 10 件の `git log` の書き方に合わせる（聞かない） |
| PR の書式と言語 | テンプレート、日本語 | `references/pr-body.md` の形・ユーザーの言語（聞かない） |
| レビュー観点 | REVIEW.md、規約の文書、レビュー指示 | code-review の既定の観点だけで見る（聞かない） |
| 禁止事項 | 「管理画面から DB を直接編集しない」「apply は確認必須」 | 無いものとして進める（聞かない） |
| チケットの置き場所と読み方 | GitHub Issues、Jira、Notion の DB | チケット番号だけ渡されたときに聞く |

各項目を**どの文書のどこで見つけたか**も状態ファイルに残す（追記先を選ぶときに使う）。

## 聞き方

- 「見つからないとき」の欄が「聞く」になっている項目だけを、**1 回の AskUserQuestion にまとめて**聞く
- 候補が出せるものは選択肢にして、推奨を先頭に置く
- 答えは状態ファイルの「プロジェクト設定」に書く。同じブランチで再開したときは聞き直さない

## 追記先の選び方

7 の報告で出す追記案（聞いたプロジェクト設定、文書にあれば防げたレビュー指摘）は、次の順で宛先を決める。

1. **同じ種類の情報が既に書かれている文書**。例: チェックコマンドが `docs/development.md` に並んでいれば、そこに足す。
   コーディング規約の文書があれば、規約の書き漏れはそこに足す
2. **入口の文書が、その種類の情報の置き場所として案内している文書**。例: README が「開発手順は docs/ を参照」と書いていれば docs/ の該当文書
3. **AI 向けの指示の置き場所**（CLAUDE.md、AGENTS.md、`.claude/rules/` のうちプロジェクトが使っているもの）。
   人が読む手順書が無く、AI の振る舞いにだけ関わる内容のとき
4. どれにも当てはまらなければ、`README.md` の開発に関する節

追記案は、宛先のファイル（と節）と、追記する文をそのまま示す。宛先を選んだ理由を 1 行添える。文書は書き換えない。
